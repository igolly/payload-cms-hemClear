# WORKFLOW.md — How this project works, and how to scale it

This is the working manual for `gary-cms`: the HemClear marketing site built on the
**Payload CMS website template** (Payload 3.88, Next.js 16, React 19, MongoDB, Tailwind 4).

Read this before adding a section, a field, or a page. The golden rule of this repo:

> **Every visual section on the site is a Payload block, rendered from page data.**
> Hardcoded JSX in a route or layout is technical debt, not a shortcut.

---

## 1. Architecture in one picture

```
Editor (admin UI)                  Database                 Frontend
─────────────────                  ────────                 ────────
/admin  ──edits──▶  Pages doc { hero, layout[] }  ──query──▶  app/(frontend)/[slug]/page.tsx
                    Globals { header, footer }                  ├─ <RenderHero {...hero} />
                    Media (uploads)                             └─ <RenderBlocks blocks={layout} />
                                                                     ├─ CallToActionBlock
                                                                     ├─ ContentBlock
                                                                     └─ …your new block
        afterChange hook ──▶ revalidatePath('/slug')  ──▶  Next cache invalidated
```

**One app, two route groups** — same Next server, same port:

| Path | Purpose |
| --- | --- |
| `src/app/(payload)/` | Admin UI (`/admin`), REST (`/api`), GraphQL. Generated — don't hand-edit, except `importMap.js` which is regenerated by a script. |
| `src/app/(frontend)/` | The public site. `[slug]/page.tsx` renders any page, `posts/`, `search/`, sitemaps. |

**Where things live**

| Concern | Location |
| --- | --- |
| Payload config (entry point) | `src/payload.config.ts` |
| Collections (repeatable content) | `src/collections/` — `Pages`, `Products`, `Media`, `Users` |
| Globals (site-wide singletons) | `src/Header/config.ts`, `src/Footer/config.ts` |
| Blocks (page sections) | `src/blocks/<Name>/{config.ts,Component.tsx}` |
| Heroes (top-of-page variants) | `src/heros/<Impact>/index.tsx` + `src/heros/config.ts` |
| Reusable field factories | `src/fields/` — `link`, `linkGroup`, `defaultLexical` |
| Access control functions | `src/access/` — `authenticated`, `anyone`, `authenticatedOrPublished` |
| Plugins (SEO, forms, redirects, search, nested docs) | `src/plugins/index.ts` |
| Seed data | `src/endpoints/seed/` |
| **Generated types — never edit** | `src/payload-types.ts` |

## 2. Daily commands

```bash
pnpm dev                  # dev server → http://localhost:3000, admin at /admin
pnpm generate:types       # REQUIRED after any config/field change → rewrites src/payload-types.ts
pnpm generate:importmap   # REQUIRED after adding/moving an admin-side React component
pnpm lint / pnpm lint:fix
pnpm test                 # vitest (int) + playwright (e2e)
pnpm build                # production build + next-sitemap
```

`pnpm generate:types` is not optional. Field config is the source of truth; TypeScript
types are downstream of it. Every block component is typed off `payload-types.ts`, so if
you skip this step your new block's props are `any` or a type error.

Env vars (`.env`, see `.env.example`): `DATABASE_URL`, `PAYLOAD_SECRET`,
`NEXT_PUBLIC_SERVER_URL`, `PREVIEW_SECRET`, `CRON_SECRET`.

## 3. The golden path: adding a new page section

This is the workflow to repeat for every new section. It is five files and two commands.
Budget ~20 minutes; do not deviate.

**Worked example:** `src/blocks/Reviews/` is a complete reference implementation of everything
below — array fields, an upload field, `collapsible` grouping, custom `RowLabel`s, a server
component, and a small `'use client'` child for the interactive part. Copy its shape.

### Step 1 — Define the block config

`src/blocks/<BlockName>/config.ts`

```ts
import type { Block } from 'payload'
import { linkGroup } from '@/fields/linkGroup'

export const TrustBadges: Block = {
  slug: 'trustBadges',                 // camelCase, unique, becomes block.blockType
  interfaceName: 'TrustBadgesBlock',   // ALWAYS set — this is what generates a named TS type
  labels: { singular: 'Trust Badges', plural: 'Trust Badges' },
  fields: [
    { name: 'heading', type: 'text', required: true },
    {
      name: 'badges',
      type: 'array',
      minRows: 1,
      maxRows: 6,
      fields: [
        { name: 'icon', type: 'select', required: true, defaultValue: 'shield',
          options: [
            { label: 'Shield', value: 'shield' },
            { label: 'Flask', value: 'flask' },
          ] },
        { name: 'label', type: 'text', required: true },
        { name: 'image', type: 'upload', relationTo: 'media' },
      ],
    },
    linkGroup({ appearances: ['default', 'outline'], overrides: { maxRows: 2 } }),
  ],
}
```

### Step 2 — Register the block on the collection

`src/collections/Pages/index.ts` → the `layout` field's `blocks` array:

```ts
blocks: [CallToAction, Content, MediaBlock, Archive, FormBlock, TrustBadges],
```

A block that isn't in this array is invisible to editors. (Posts embed a smaller set —
`Banner`, `Code`, `MediaBlock` — inside rich text via `BlocksFeature`; add there only if
the section should be insertable mid-article.)

### Step 3 — Regenerate types

```bash
pnpm generate:types
```

This adds `TrustBadgesBlock` to `src/payload-types.ts` and widens `Page['layout'][0]`.

### Step 4 — Build the React component

`src/blocks/<BlockName>/Component.tsx`

```tsx
import React from 'react'
import type { TrustBadgesBlock as Props } from '@/payload-types'
import { CMSLink } from '@/components/Link'
import { Media } from '@/components/Media'

export const TrustBadgesBlock: React.FC<Props> = ({ heading, badges, links }) => {
  return (
    <section className="w-full bg-white px-6 py-16 lg:px-8">
      <div className="mx-auto max-w-7xl">
        <h2 className="font-serif text-3xl text-[#1c2f6e]">{heading}</h2>
        {Array.isArray(badges) && badges.length > 0 && (
          <ul className="mt-8 grid grid-cols-2 gap-4 lg:grid-cols-4">
            {badges.map((badge, i) => (
              <li key={badge.id ?? i}>{badge.label}</li>
            ))}
          </ul>
        )}
      </div>
    </section>
  )
}
```

Rules for block components:

- **Server components by default.** Only add `'use client'` when you need state, effects,
  or event handlers. The current `HighImpactHero` is a good model: it was converted from a
  client component to a server component when the `useHeaderTheme` effect was removed.
- **Guard every optional field.** Editors publish half-filled blocks. `Array.isArray(x) && x.length > 0`,
  `media && typeof media === 'object'` — relationships arrive as an ID string when not populated.
- **Key on `item.id ?? i`.** Payload array rows carry stable `id`s; use them.
- Use `<Media resource={…} />` for uploads, `<CMSLink {...link} />` for links,
  `<RichText data={…} />` for lexical fields. Never a raw `<img>` or `<a>` to internal pages.

### Step 5 — Wire into the renderer

`src/blocks/RenderBlocks.tsx`

```ts
const blockComponents = {
  archive: ArchiveBlock,
  content: ContentBlock,
  cta: CallToActionBlock,
  formBlock: FormBlock,
  mediaBlock: MediaBlock,
  trustBadges: TrustBadgesBlock,   // key MUST equal the block `slug`
}
```

### Step 6 — Seed it (optional but recommended)

Add representative content to `src/endpoints/seed/home.ts` so a fresh database renders a
complete page and so the design has real copy to lay out against.

### Checklist

- [ ] `src/blocks/<Name>/config.ts` with `slug` + `interfaceName`
- [ ] Registered in `Pages.layout.blocks`
- [ ] `pnpm generate:types`
- [ ] `src/blocks/<Name>/Component.tsx` typed off `@/payload-types`
- [ ] Registered in `RenderBlocks.tsx` under the same key as `slug`
- [ ] Verified at `/admin` (create the block) **and** on the page
- [ ] `pnpm lint` clean

## 4. Heroes vs. blocks — which do I use?

The hero is a **group field on the page**, not a block. There is exactly one per page, it
sits above `layout`, and the variant is chosen by `hero.type`.

- Adding a field to an existing hero variant → `src/heros/config.ts`, gated by
  `admin.condition: (_, { type } = {}) => type === 'highImpact'`, then update
  `src/heros/<Impact>/index.tsx`. This is how `badgeTitle`, `heading`, `benefits` and
  `trustPoints` were added to High Impact.
- A brand new hero layout → add a value to the `type` select, create
  `src/heros/<NewImpact>/index.tsx`, register it in `src/heros/RenderHero.tsx`.
- **Anything that could appear more than once, or in a different order → make it a block.**

Two conventions worth copying from the current hero:

- `textarea` + `.split('\n')` for copy where the designer controls the line wrap.
- `select` of icon names mapped to a component lookup (`trustIcons`) rather than letting
  editors paste SVG.

| Savings Compare | `savingsCompare` | "Buying separately" vs the formula, with savings |

Plus the template's originals: `cta`, `content`, `mediaBlock`, `archive`, `formBlock`.

**Icons** come from `src/components/BrandIcons/index.tsx` — a name→SVG registry with a
matching `brandIconOptions` list, so editors pick from a dropdown instead of pasting markup.
To add one: draw it in the registry, add its key to `brandIconOptions`, and it is available
to every block using an icon `select`.

**Image placeholders**: `src/blocks/FAQ/ImagePlaceholder.tsx` exports `ImageSlot`, which
renders the uploaded media or a dashed box holding its space. Use it for every `upload`
field so half-filled blocks look deliberate rather than broken.

**Carousels**: `src/blocks/VideoStories/Carousel.tsx` is the pattern — a native
`overflow-x-auto` + `snap-x` track, with arrows and dots driving `scrollTo` and the active
index derived from `scrollLeft`. Touch swipe and keyboard scrolling come free, and no
carousel library is needed. Copy it rather than adding a dependency.

**Auto-numbering**: `waysGrid` renders `{index + 1}.` rather than storing the number, so
reordering rows in the admin renumbers the page. Do the same for any ordered list.

**Wide content scrolls inside itself**: the `comparison` table sets `min-w-[46rem]` inside an
`overflow-x-auto` wrapper, so it scrolls horizontally on a phone without the page scrolling
sideways. Any table or wide diagram must do the same.

**Inline formatting** (a bold phrase mid-sentence) is a `richText` field rendered with
`<RichText enableGutter={false} />` — see `pairing.intro` and `totalCare.subheading`. Don't
invent markup conventions inside a `text` field for this.

**Positional arrays**: in `comparison`, each row's `values` array maps to `products` by
index — the nth value belongs to the nth column. It keeps the admin simple, but reordering
columns does not reorder the values. Say so in the field description whenever you couple two
arrays this way.

**Derive UI lists from the content, don't ask editors to maintain them twice.**
`ingredientExplorer` builds its category filter pills from the `category` field on each
ingredient, in first-appearance order — there is no separate categories array to fall out of
sync with the cards. Same principle as `waysGrid` numbering itself from position.

**Reach for an existing block before writing a new one.** `/about-hemorrhoids` is 10 sections
and needed **zero** new blocks — `featureStrip` runs six times across four layout variants,
`causes` twice, `totalCare` once. The `/why` page is 8 sections and needed exactly one: `causes` runs three times (twice with `imagePosition: 'right'`),
`featureStrip` three times (different backgrounds, one with a CTA), plus `totalCare` and
`waysGrid` once each. When a design almost fits an existing block, add the *option* it is
missing — `imagePosition`, `eyebrow`, `footnote`, `background`, `align` — rather than forking
a near-duplicate. Every option added this way is defaulted to preserve existing pages.

**Full-bleed blocks**: `RenderBlocks.tsx` keeps a `fullBleed` set. The template's original
blocks sit in a centred container and rely on the wrapper's `my-16` for spacing; every block
in this project paints edge-to-edge and owns its own `py-*`. **Add your block's slug to that
set** or it renders with a stripe of page background above and below it.

**Nav and footer links are internal references, not typed URLs.** `src/fields/link.ts` allows
`pages`, `posts` and `products`; `CMSLink` builds the href as `/<relationTo>/<slug>` (pages get
no prefix), so a reference link follows the document if its slug changes. Only use a custom URL
for a destination that has no document.

**The announcement bar is a Header global field**, not a block — it belongs to the site
chrome, not to a page. `announcementEnabled`, `announcementTitle`, `announcementText` and
`announcementEndsAt` live on the Header global; `src/Header/AnnouncementBar/index.tsx` is the
client island. Its countdown renders empty on the server and fills in after mount, because a
live clock rendered during SSR can never match the client's first paint.

### The footer is a global, not a block

`src/Footer/config.ts` was rebuilt to match the design and now holds `columns` (each with
its own link list), `promiseItems`, `socialItems`, `legalLinks`, `tagline`, `copyright` and
`disclaimer` — the old `navItems` field is gone, and `src/endpoints/seed/index.ts` seeds the
new shape. Social marks live in `socialIcons` / `socialIconOptions` in `BrandIcons`,
separate from `brandIcons` so the two dropdowns stay distinct.

### Cleared debt (was: hardcoded sections)

`src/app/(frontend)/components/HemClearSections.tsx` used to be imported by
`layout.tsx`, which meant its three sections rendered on *every* route — including
`/posts`, `/search` and 404s — with no copy editable in the CMS. It has been removed from
the layout and replaced by the `causes` and `productSystem` blocks, and its two images now
live in the Media collection rather than `public/`. The file itself is still on disk and
unreferenced; it can be deleted.

Still in `public/` and not yet in Media: `hero.png`, `hero-image.jpg`, `logo.png`,
`reviw.png`, `faq.png`, `sectionshomepage.png` (the last three are design references, not
site assets). `scratch_shot.mjs` is a throwaway screenshot script that shouldn't be committed.

## 6. Data flow, caching, preview

- **Static generation.** `[slug]/page.tsx` runs `generateStaticParams()` over all published
  pages. `queryPageBySlug` is wrapped in `cache()` so page + metadata share one query.
- **Revalidation is hook-driven.** `src/collections/Pages/hooks/revalidatePage.ts` calls
  `revalidatePath()` on `afterChange` and `afterDelete`; the Header/Footer globals have
  their own `revalidateHeader`/`revalidateFooter`. **If you add a new collection or global
  that renders on the frontend, you must add its revalidate hook** — otherwise editors
  publish and see nothing change.
- **Drafts + autosave.** Pages have `versions.drafts.autosave` at a 100 ms interval, tuned
  for live preview, plus `schedulePublish`. Draft reads go through `draftMode()`.
- **Live preview** is configured in `payload.config.ts` (mobile/tablet/desktop breakpoints)
  and per-collection via `generatePreviewPath`. `<LivePreviewListener />` refreshes the
  route on autosave — it's already mounted, don't add another.
- **Access control** is per-collection: `read: authenticatedOrPublished` means unpublished
  drafts are invisible to the public. Never widen this to `anyone` on `Pages`/`Posts`.
- **Globals are cached by slug *and* depth** (`src/utilities/getGlobals.ts`). The depth was
  originally left out of the cache key, so two callers asking for the same global at
  different depths shared one entry and whichever ran first won — a silently stale render.
  Keep `depth` in `keyParts` if you touch that file.
- **Writing content from a script skips revalidation.** `context: { disableRevalidate: true }`
  is required outside a request (see below), which means the `unstable_cache` entry survives
  the write. In dev, stop the server, `rm -rf .next/cache`, restart. Editing through `/admin`
  has none of this problem — the hook runs inside a request and revalidates properly.

### Click-to-edit (custom)

Payload's live preview is one-directional — the admin streams data into the iframe, but
ships no channel back. This repo adds one so clicking a section in the preview opens that
block in the editor:

| Side | File | Job |
| --- | --- | --- |
| Iframe | `src/components/VisualEditorBridge/index.tsx` | Delegated click listener; finds the nearest `[data-payload-path]` and `postMessage`s the path to the parent. Mounted only in draft mode. |
| Admin | `src/components/VisualEditorTarget/index.tsx` | Registered as an admin **provider**; receives the message, switches tabs, expands the collapsed row, scrolls, flashes, focuses the first input. |

Two levels of tag:

- `data-payload-path` — the **block**. Applied automatically in `RenderBlocks.tsx`
  (`layout.${index}`), so a new block is clickable the moment it renders, no extra work.
  The hero is tagged `hero` in `RenderHero.tsx`.
- `data-payload-subpath` — an **individual field**, relative to the containing block:
  `data-payload-subpath={\`featured.${i}.quote\`}`. The bridge resolves it against the nearest
  ancestor block, so **block components never need to know their own index in `layout`**.
  Deepest tag wins, so a card can carry a coarse fallback while its text carries exact fields.

Add subpaths when you build a block — it is one attribute per rendered field. Live examples:
`src/blocks/Reviews/Component.tsx`, `ReviewGrid.tsx`, `src/heros/HighImpact/index.tsx`.

Resolution is progressive: `layout.1.featured.2.quote` → `layout.1.featured.2` →
`layout.1.featured` → `layout.1`, so a click always lands somewhere useful even if the exact
leaf has no field wrapper of its own.

It relies on Payload's admin DOM contract, which is not a public API and could change on
upgrade. Verified against **3.88.0**:

- blocks row → `id="<parentPath with dots as dashes>-row-<index>"` (e.g. `layout-row-0`)
- **array** row → `id="scroll-<random componentId>-row-<index>"` — *not* path-addressable, which
  is why nested content is targeted by its leaf field id instead
- any other field → `id="field-<path with dots as double underscores>"` (e.g. `field-hero__heading`)
- collapsed row → `.collapsible--collapsed`, opened by clicking `.collapsible__toggle`
- inactive tab → `button.tabs-field__tab-button`

If click-to-edit silently stops working after a Payload upgrade, re-check those four
selectors first — grep `node_modules/@payloadcms/ui/dist` for `` id: `field-${ `` and
`baseClass = 'collapsible'`.

## 7. Conventions

- **Imports:** `@/` maps to `src/`. Use it; avoid `../../../`.
- **Formatting:** Prettier — single quotes, no semicolons, 100 print width (see
  `.prettierrc.json`). `HemClearSections.tsx` uses double quotes and semicolons because it
  was pasted in from elsewhere; new files follow the repo style.
- **Styling:** Tailwind 4 utility classes inline. **The brand blue is a token, not a hex** —
  `--color-brand` (`#0023a3`) and `--color-brand-dark` are declared in the `@theme` block of
  `src/app/(frontend)/globals.css`, so use `bg-brand`, `text-brand`, `border-brand` and
  `hover:bg-brand-dark`. Changing the brand colour is a one-line edit there; it used to be 176
  hardcoded hexes across 34 files. `--color-navy` (`#192f7c`) is the deeper band colour, used
  by `bg-navy` where the brand blue reads too bright — currently the announcement bar and the
  Video Stories section. Headings use two tokens: `text-heading`
  (`#192f7c`) for main section headings — `h1`/`h2` and any full-width section title — and
  `text-subheading` (`#0329b2`) for smaller card titles (`h3`/`h4`). Headings on a dark band
  stay `text-white`. Light section
  background `#F4F8FF`, borders `#DBE8FA`.

  The three colour tokens live together in the `@theme` block:

  ```css
  --color-brand:      #0023a3;  /* CTAs, icons, UI accents */
  --color-navy:       #192f7c;  /* full-width dark bands */
  --color-heading:    #192f7c;  /* main section headings (h1/h2) */
  --color-subheading: #0329b2;  /* card titles (h3/h4) */
  ```
- **Icons:** `lucide-react` for standard icons; hand-rolled inline SVG only when lucide has
  no equivalent (as in the `Laurel` mark and the medical icons).
- **Do not edit:** `src/payload-types.ts`, `src/app/(payload)/**` (except via
  `generate:importmap`), `.next/`, `tsconfig.tsbuildinfo`.
- **The `<!-- BEGIN:nextjs-agent-rules -->` block in `CLAUDE.md`** is rewritten by
  `next dev`. Commit it with your work rather than reverting it.

## 8. Adding other things

### Page types

Not every page is a `Pages` doc with a `layout`. A **page type** with a fixed structure is
its own collection:

| Collection | Route | Shape |
| --- | --- | --- |
| `pages` | `/[slug]` | hero + free-form `layout` blocks — use for marketing pages |
| `products` | `/products/[slug]` | fixed PDP: gallery, buy box, results, detail sections |

`Products` is the worked example of a structured page type. Its fields are grouped into admin
**tabs** (Overview / Results / Buy Box / Details / SEO) because a flat list of ~30 fields is
unusable. The page itself is `src/app/(frontend)/products/[slug]/page.tsx`, composed in
`src/components/ProductDetail/` from one server component plus three small client islands
(`Gallery`, `BuyBox`, `DetailSections`) — only the interactive parts ship JS.

`Products` also has its own `layout` blocks field (Sections tab), so **every site block can
run below the product detail** — the list lives in `src/collections/Products/blocks.ts`.
`RenderBlocks` accepts either collection's layout, so the renderer is shared rather than
duplicated. Full-bleed blocks must render *outside* the product's padded container, which is
why `ProductDetail` closes its `<section>` before calling `RenderBlocks`.

**Components take layout classes as props rather than hard-coding them.** `Carousel` is used
full-width on the home page and inside the narrow product column; it takes `itemClassName`
for card width instead of guessing from the viewport, because a viewport breakpoint says
nothing about the width of the container it was dropped into.

A new collection needs a **revalidate hook** (`src/collections/Products/hooks/revalidateProduct.ts`)
and an entry in the `collectionPrefixMap` in `src/utilities/generatePreviewPath.ts`, or live
preview and draft preview will point at the wrong URL.

**Gotcha — `postcss.config` must be `.mjs`.** With `"type": "module"`, Turbopack's PostCSS
loader fails to evaluate a `postcss.config.js` and the build dies with
`TypeError: __turbopack_context__.a is not a function`, pointing at whichever CSS file it hit
first. The extension is the fix; don't rename it back.

**Gotcha — creating the first document in a new Mongo collection fails inside a transaction.**
MongoDB cannot implicitly create a collection within a multi-document transaction, so the very
first `payload.create` on a new collection aborts with `NoSuchTransaction` (wrapping an
`AtlasError 8000`). Pass `disableTransaction: true` for that first write, or create the
collection first. Only affects scripts seeding a brand-new collection.

**A new collection** (e.g. `Testimonials`):
1. `src/collections/<Name>.ts` — set `access` (start from `authenticated` +
   `authenticatedOrPublished`), `admin.useAsTitle`, `slugField()` if it gets a URL.
2. Register in `payload.config.ts` → `collections: [...]`.
3. Add a revalidate hook if it renders on the frontend (§6).
4. `pnpm generate:types`.

**A new global** (site-wide singleton): mirror `src/Header/config.ts`, register under
`globals: [...]`, add an `afterChange` revalidate hook, `pnpm generate:types`.

**A new admin UI component** (RowLabel, custom field, dashboard widget): create it,
reference it by import path string (`'@/Header/RowLabel#RowLabel'`), then
`pnpm generate:importmap`. The string path — not a direct import — is what Payload expects.

**A new form:** use the form-builder plugin at `/admin/collections/forms`; drop a
`FormBlock` onto the page. Don't hand-roll a form component.

## 9. Definition of done

1. `pnpm generate:types` run and `src/payload-types.ts` committed.
2. Feature verified in `/admin` (create it, save it, empty-field case doesn't crash) and on
   the rendered page at mobile + desktop widths.
3. `pnpm lint` clean, no new TS errors.
4. Seed data updated if the section belongs on the home page.
5. No new hardcoded copy or images in a route/layout file.
